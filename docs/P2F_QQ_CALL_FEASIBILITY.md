# QQ电话与自定义音频评估

日期：2026-11-03。结论：暂缓，不作为普通文字提醒的准出条件。

检查了项目锁定NapCat Node v4.18.41的napcat.mjs动作注册、现有aiocqhttp通道、[NapCat公开请求接口](https://napneko.github.io/develop/api)和[OneBot 11公开API](https://github.com/botuniverse/onebot-11/blob/master/api/public.md)。公开接口支持文字/语音消息，但未发现可靠受支持的“拨打QQ电话→确认对方接听→接入指定音频流”完整链路。此判断是基于接口列表和锁定实现的工程推断，不声称QQ客户端内部不存在通话能力。

现有语音消息发送接口不能等同QQ电话。自定义通话信令、接听状态和音频注入需要另行研究未稳定公开的客户端能力，维护成本和失败风险明显高于普通提醒；若上游以后提供完整公开接口，仍需重新评估授权、重复拨号、超时和挂断。

开发成本判断：当前无法给出可靠实现工期；非公开信令与音频注入属于较高成本研发，按周量级而非普通提醒的小改动估计，且缺少稳定验收依据。此为估算，不是交付承诺。

本轮不模拟QQ客户端、不使用Computer Use、不拨号、不接受或保存电话提醒音频。/reminder audio明确返回暂缓；任何伪装文件名、路径或URL都不会由该入口下载或打开。将来若启用音频上传，须单独实现大小、实际文件魔数/解码、时长、格式、来源、路径隔离和清理策略，不能只看扩展名。音频上传/解码不计为本轮已实现或已测试。
