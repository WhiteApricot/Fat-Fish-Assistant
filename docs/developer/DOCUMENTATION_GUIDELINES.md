# 文档与工程治理规范

## 归属

- 用户文档和平台接入指南沿用 `docs/` 现有入口。用户文档说明操作和限制，平台文档说明各自的认证、配置和原生行为。
- 开发者文档集中在 `docs/developer/`，记录当前架构、程序行为、接口与兼容边界。
- 后续工作统一登记在[路线图](../ROADMAP.md)。历史规划与过程材料放入本地历史索引、报告或归档。公开归档须有持续参考价值，并标注时间、基线、适用范围和替代文档。

## 每次变更

1. 从当前 main 确认源文件、入口、配置及相关测试。阶段、分支和验收统一引用路线图中已登记的编号。
2. 修改程序行为时同步更新对应开发者文档。用户操作或限制变化时同时更新用户或平台文档。
3. 记录稳定架构、数据及作用域、接口输入输出、生命周期和状态转换、权限检查、错误与降级、扩展方式、外部依赖和运行限制。区分宿主与 FFA 的职责。
4. 说明现有实现、尚未接入的代码和计划之间的差异。失效设计应修正、移出当前索引或归档。
5. 检查相对链接、代码符号、版本前提和差异。仅文档变更检查内容与链接，程序变更运行相关回归和项目规定的 CI。发现问题超出本阶段范围时记录复现与影响，交给对应阶段。

## 证据和私有数据

正式文档可保留日期和阶段结论。逐项验收、测试日志、探针、截图、临时调试、GPT/Codex 执行日志、分支过程和未经确认的推测归入本地测试或报告目录。测试代码和可公开的最小夹具按仓库测试规则提交。

仓库只跟踪通用规范和公开配置示例。机器路径、真实账号、Token、Cookie、平台凭据、私有插件与依赖目录、运行数据库、本地配置和测试数据应留在受控目录。提交前检查索引和忽略规则。凭据曾进入 Git 时，按泄露处理并更换凭据。
